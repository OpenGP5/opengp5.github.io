Protocols

USB-MIDI, the firmware update, the image format, and the link between the processors.

This page covers USB commands, update steps, image files and the serial link between chips. Read How a firmware works to see where each part fits.

Notation

Byte sequences use hexadecimal (base 16). For fields longer than one byte, use little-endian order unless noted: send the least significant byte first. Angle brackets mark fields in a command. Square brackets mark parts you can leave out. In frame diagrams, brackets group the fields.

MarkMeaning
u8, u16, u32, u64Unsigned whole numbers of 8, 16, 32 or 64 bits
i16Signed 16-bit whole number
f3232-bit float
NULZero byte
ACKReply that accepts a message
NAKReply that rejects a message or asks for a retry
NibbleFour bits, or half a byte

Commands marked 1.0 belong to the API that began in platform 0.7. These docs target platform 1.0.0. See Versions.

1. USB-MIDI framing

The pedal uses USB-MIDI to send and receive frames. Each frame is one System Exclusive (SysEx) message:

F0  <body, every byte sent as two bytes: high nibble, then low nibble>  F7

body = crc8, class, index, length, payload[length]
crc8 = CRC-8, polynomial 0x07, initial value 0, not reflected,
       over the bytes 00, class, index, length, payload

Class 0x01 sends a command with index 0. Class 0xFF sends update data. For data, the index is an 8-bit packet number that wraps back to 0. The pedal replies to update frames with 14 08 00. A non-zero third byte asks for the frame again.

tools/gp5_link.py wraps 7E 00, 7E 01, 7E 03 / 7E 04, 7E 05 (flash-read) and the 1.0 commands (info, params, set, presets, preset, log, status). tools/gp5tool.py info reads 7E 16 too.

The state query 12 30 gets a reply from Valeton’s app or the factory loader:

StateReply
Valeton app11 30 01 00
Update mode11 30 01 01
OpenGP5 appNo reply to this query

gp5tool.py status uses those replies and the USB port name (OpenGP5 from 1.0, GP-5 Open FW before, GP-5 for Valeton’s firmware and the loader) to tell the states apart.

Reply rules from 1.0: add new fields at the end. Keep old fields in place with the same meaning. Keep command numbers fixed. A reader must use the fields it knows and skip extra bytes. For new features, add a command or sub-command, such as 7E 17 5. Old tools can keep using the old commands. They need an update to use the new features.

3. Firmware update session (factory loader)

Start update mode with 11 6F, or press and hold the foot switch and PARA while plugging the pedal in. Release both controls, then confirm update mode with gp5tool.py status or Launchpad. Use the reported state, not the screen alone. One update session writes one or more sections.

The platform restarts the chip before handing control to the loader. It writes a mark in the top 32 bytes of RAM at 0x20047FE0, outside the app’s RAM. On restart, the platform sees the mark before starting the link or firmware and enters the loader. This avoids a loader crash seen after direct handover from an active audio link. The extra restart takes about one second; the tools wait for it.

Send these frames in order. Wait for the loader to reply with 14 08 00 after each frame:

StepBytesWhat happens
ENTER11 60the session starts
BEGIN11 61 <type> 00 00 00 <packet count u32> <length u32>the loader erases that section
DATA, once per packetclass 0xFF, index = the packet number; 19 bytes each: 11 <type>, then the section’s datathe data is written
END11 6E <type> 00the section is done; BEGIN … END again for each further section (dsp, app, …)
END_IMAGE11 6E 6E 00the pedal restarts

length includes the two leading bytes 11 <type>. The loader can write the sections below, but not its own code at 0x0–0xFFFF. This preserves entry to update mode. A separate DSP updater fault can still block a flash; see J7 recovery.

SectionTypeDestinationMaximum size
dsp (DSP firmware)0x63DSP flash 0x400064 KB
dsp-data (Valeton)0x67DSP flash1 MB
models (Valeton)0x66DSP flash268 KB

4. Image format (.bin)

Valeton’s updates and this project’s builds use the same container. Little-endian:

0x00  'HTFW'                     0x0C  product name, 16 bytes ("GP-5")
0x08  u32 total file size        0x1C  'V' major minor patch (shown by Valeton's updater only)
0x21  u8 compression (0 = none)  0x22  u8 section count       0x24  u32 payload length
0x38  section table, 16 bytes per section:
        u16 CRC-16/MODBUS of the data, stored byte-swapped, u8 0, u8 type,
        u32 flash address, u32 offset of the data after the table, u32 length
      then the section data, in table order

A Valeton image has all five sections. An OpenGP5 build has two: dsp and app. Use the order and addresses in the section table above. Run gp5tool.py check to check a file without a pedal.

5. Link between the processors (UART)

The control chip’s UART0 (pins A0 receive / A1 transmit) and the DSP’s UART0 (0x40005000): 460800 baud, 8N1. Frames in both directions:

[crc8][length u16 = whole frame][01][payload]        crc8 as in section 1, over the payload only
payload = [cmd u16][len u16][fields…]
status-only answer: 01 04 00 14 = ACK, 01 04 00 13 = NAK (bad CRC or length)

Commands the platform uses:

CommandSenderPayload / reply
0x6000controlversion query, [cmd][8][0 u32] → [cmd][12][1 u32][version u32]. The control side waits for this answer before anything else.
0x1001controloutput level: [cmd][12][sub 0 u32][f32 0.0 … 1.0] → ACK. The DSP is muted until it gets one.
0x4001DSPa 24-byte status frame about every 43 ms (zeros today); not answered
0x7F01 / 0x7F02controlDSP flash tick patch: status / apply (see platform/dsp/tickpatch.h)
0x7F04controlDSP load: [cmd][8] or [cmd][12][1 u32] (clear peak readings) → [cmd][24][cycles last block][worst since start-up][late blocks][variables in use, bytes][GP5_LARGE in use, bytes] (1.0: the last two)
0x7F06controlUSB audio (1.0): [cmd][12][off u32][0 u32] → ACK. 1 = leave the firmware’s sound out of the outputs (the computer’s playback stays); glides over a block
0x7F10controla parameter (1.0): [cmd][12][id u32][value u32] → ACK; the DSP keeps it and calls fw_param()
0x4F10DSPa log line (1.0, gp5_log): [cmd][len][text], not answered; the control chip adds it to its log as dsp: …
0x7F11 … 0x7FFFcontrolthe firmware’s own commands, handed to fw_command() (platform/dsp/gp5_dsp.h; from 0x7F10 for a firmware without parameters)

Any other command is acknowledged.
