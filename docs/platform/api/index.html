API reference

Everything a firmware can use: manifest, callbacks, platform calls, log, load.

This page lists the public calls, callbacks and manifest fields. Read each header’s comments for full call details. An API is the set of calls and commands your effect can use. These docs target platform 1.0.0. See Versions for the distinction. Start with How a firmware works, then use these guides: parameters, UI kit, audio link, performance, debugging, simulator, releasing, storage, fonts, questions.

Each firmware folder needs firmware.json. The build rejects a folder without it. Platform 0.8 removed the older 0.6 API, which allowed builds without a manifest.

A firmware’s folder

my-effect/
  firmware.json        who it is and what it needs (below)
  params.h             its parameters (optional; params.md)
  dsp/firmware.h       the sound: fw_init, fw_process, fw_command, fw_param      (gp5_dsp.h)
  nds32/*.c            screen and controls: fw_draw, fw_foot_down, ...          (gp5_firmware.h)

Keep your effect under firmwares/, or put it in your own Git project with a pinned copy of OpenGP5. Git calls that copy a submodule. In that case, pass your effect folder’s path to the build.

The firmware template sets this up. GitHub Actions tests and builds each push. A tag can publish a release. You can also build in a browser with GitHub Codespaces. See firmwares/tremolo for a full example.

Run python3 platform/manifest.py <folder> --check to validate the fields. Use your firmware folder’s path. The build creates definitions for both chips: GP5_FW_ID, GP5_SAMPLE_RATE, GP5_CTL_MHZ, GP5_AUDIO_LINK, GP5_LINK_WORDS, GP5_PRESETS, GP5_HAS_PARAMS, GP5_BLUETOOTH and GP5_USB_AUDIO (with USB audio also GP5_LINK_TOTAL, GP5_USB_PLAY_AT, GP5_USB_REC_AT or GP5_USB_RECORD_CONTROL).

The image stores the manifest with its code, in a metadata block. The tools read it to show the build’s name and version before a flash. Run gp5tool.py info <file.bin> to read a file. The pedal sends the same details through USB command 7E 16.

Control processor: what the platform calls

You can omit these callbacks. The platform uses an empty function in their place. They run in the main loop, so do not wait for events inside them. A blocked loop turns the LEDs full red after two seconds. See Performance for shorter response-time targets.

Bluetooth

To send MIDI over Bluetooth, set "bluetooth": true. The pedal uses Bluetooth Low Energy MIDI (BLE-MIDI). It shows the name GP-5 and accepts one host at a time. Connect with a phone or a BLE-MIDI host on your computer. On a Mac, use Audio MIDI Setup › Bluetooth.

The radio starts while the logo shows. Calibration takes about one second and runs before the audio link. Starting the radio during an active link caused sound stops in testing.

  • MIDI messages reach fw_midi through the same callback as USB MIDI.
  • The computer’s commands (SysEx) work over it too: macOS names the port “OpenGP5 Bluetooth” (“GP-5 Bluetooth” before 1.0); Launchpad and gp5_link.py (GP5_PORT="OpenGP5 Bluetooth") use it. Firmware updates need USB.
  • Each pedal has its own address (from the chip’s efuse).
  • The radio uses a short control-chip interrupt per event, 7.5 to 30 ms apart. It also uses 4 KB of RAM outside your firmware’s budget. The radio code is OpenGP5’s own (platform/nds32/bt/).

DSP

One header, dsp/firmware.h, compiled into the platform’s DSP program:

CallbackWhen it runs
static void fw_init(void)once, before audio starts
static void fw_process(const int32_t *in, int32_t *out_left, int32_t *out_right)every block: 64 samples, mono in, stereo out, full scale ±2³¹. The platform applies the output level afterwards
static void fw_param(uint32_t id, int32_t value)a parameter changed, before the next fw_process (a firmware with params.h defines it, even empty)
static int fw_command(uint32_t cmd, const uint8_t *p, uint32_t n)the firmware’s own link commands from 0x7F11; return 0 for one it doesn’t know

The DSP budget is about 278,000 cycles per block at 44.1 kHz or 255,900 at 48 kHz. Code runs from flash unless you mark it for RAM. See Performance.

The audio link

Set "audio": {"link": true} to exchange link_words 32-bit values each way per audio block. On the control chip, call gp5_link_start(on_block) in fw_init. The handler runs in an interrupt and must finish within one block.

On the DSP, read received words with gp5_link_in() and fill outgoing words with gp5_link_out(). A sample sent from the DSP returns from the control chip three blocks later: about 4.4 ms at 44.1 kHz or 4 ms at 48 kHz.

With link_early, the exchange starts at the beginning of the block. Define static void fw_link_early(const int32_t *in, int32_t *out) to supply new input before that exchange. See The audio link for the full example and timing rules.

USB audio

A firmware written for platform 1.0 or later is a class-compliant USB audio interface unless firmware.json says "usb_audio": false. A firmware written for an older platform (or that doesn’t say) gets it only with "usb_audio": true. The pedal then shows up beside its USB-MIDI port (no driver on macOS, Windows or Linux): 2 channels each way, 16-bit, at the firmware’s sample rate.

  • Recording (pedal → computer) is the firmware’s finished stereo output, taken on the DSP after fw_process, before the computer’s playback is mixed in and before the volume knob. It reaches the computer sample for sample (the pedal sends 44 or 45 frames a millisecond, one more or fewer as its clock drifts from the computer’s).
  • Playback (computer → pedal) is mixed into the outputs on the DSP, before the volume knob. The control processor resamples it from the computer’s clock to the DSP’s (they differ by tens of ppm).
  • Direct sound. While the computer plays into the pedal, the pedal’s own sound can be left out of the outputs, so a DAW that monitors the pedal isn’t heard twice: gp5_usb_audio_set_direct(0) (1, the default, puts it back; gp5_usb_audio_direct() reads it). The computer can switch it too (Launchpad’s pedal panel, gp5_link.py direct off, 7E 19). Recording doesn’t change, and while nothing plays the pedal is always heard. It is back on after a restart, unless the firmware stores it and sets it again in fw_init.
  • It travels in the audio link: the platform keeps 64 words each way after the firmware’s own link_words, and starts the link for a firmware that has none. So a firmware has at most 200 link words while USB audio is on.
  • A firmware that finishes its sound on the control processor (NAM Loader) sets "usb_audio": {"record_from": "control"} and hands the output over from on_block: gp5_usb_audio_record(left, right), 64 samples each, full scale ±2^31 (a block it doesn’t hand over is recorded as silence, so the recording keeps its place). No words come back from the DSP for it then: link_words may be up to 264, but its own words towards the DSP must stay below 200 (the platform’s playback words are 200..263).
  • Cost: on the control processor the USB interrupt (0.9 %) and the resampler in the link’s interrupt (about 3 % of a block, 6 % at worst); on the DSP a copy and a mix of 64 frames. "usb_audio": false gives all of it back.

Log

gp5_log("rate %ld, depth %d %%", rate, depth) on either processor. printf-style (%d %u %x %s %c %f, width, precision; gp5_fmt.h), at most about 110 characters a line, stamped with the time. The control chip keeps the last 4 KB; the DSP’s lines travel over the link and are marked dsp:. uint32_t is a long on both processors: print it with %lu / %lx. A DSP line costs a few thousand cycles: not every block.

python3 tools/gp5_link.py log -f        # follow it while you play

On the computer (tools/run_effect.py) the DSP’s gp5_log prints to the terminal.

Load and memory

python3 tools/gp5_link.py status [--reset]

The command shows current and peak block load, the longest main-loop pass, late blocks and memory use. Add --reset to clear peak readings. Test with the settings that use the most time before a release.

Trying things without a pedal

python3 tools/simulate.py tremolo --script controls.txt --in guitar.wav

The simulator runs both halves and the audio link with a control script. It saves screen images as PNGs and sound as a WAV file. To run the DSP half alone, use python3 tools/run_effect.py tremolo in.wav out.wav --set Rate=800 --set Shape=Square.

Versions

These docs target platform 1.0.0. Its API was introduced in 0.7, so firmwares written for 0.7 or 0.8 build on 1.x unchanged; they get USB audio only if they ask for it ("usb_audio": true).

Read the running platform version from GP5_VERSION_TEXT in gp5_firmware.h. Set firmware.json’s platform field to the major and minor release your code needs, such as "1.0". The build rejects a newer minor version or a different major version.

1.x guarantees

Every 1.x release preserves these parts:

  • Public calls, callbacks, their timing and manifest fields keep their meaning.
  • Saved parameters, presets, store records and files remain readable.
  • USB commands keep their numbers and existing fields. New reply fields go at the end.
  • The platform stays within its memory share, leaving at least the documented firmware budgets.

See Known limits for those budgets and Protocols for reply rules. Continuous integration (CI) runs build and test checks on changes. tools/check_budget.py checks memory use, and tools/test_compat.sh checks the fixtures in compat/1.0. The fixtures are the passthrough, the tremolo and the template as written for 1.0, and NAM Loader 1.3.1 as written for 0.8.

In 1.x, GP5_DEPRECATED warns that a call will go away. The warning must stay for at least one full minor release. A later major release can then remove the call. The guarantees do not cover code inside the platform or UI-kit struct layout beyond the fields you set. Limits such as link size and preset count may grow.
