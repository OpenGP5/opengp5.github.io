The audio link

Sound on both chips.

The audio link exchanges 32-bit words between the two chips after each audio block. A word is one 32-bit value. Send guitar samples to the control chip, process them there, and read the result on the digital signal processor (DSP).

The control chip can suit code that needs more time or memory:

  • it has a 264,160-byte firmware RAM budget, compared with the DSP’s 19,712 bytes plus 122,880 bytes;
  • it ran the same float code about 1.7 times faster;
  • with its integer DSP instructions, fixed-point code is much faster again (performance).

NAM Loader runs most of its amp model there. Dreamcatcher runs its whole engine there and mixes on the DSP.

The result returns three blocks later: about 4.4 ms at 44.1 kHz or 4 ms at 48 kHz. Keep the dry path on the DSP to avoid adding this round-trip delay to it.

The smallest example

The guitar goes to the control chip, gets a soft clip there, and comes back.

firmware.json: ask for the link and how many words each way:

{ "id": "link-demo", "name": "Link demo", "version": "0.1.0", "platform": "1.0",
  "audio": { "link_words": 64 } }

dsp/firmware.h:

static void fw_init(void) {}

static void fw_process(const int32_t *in, int32_t *out_left, int32_t *out_right)
{
    const int32_t *back = gp5_link_in();       /* the control processor's words: a block from 3 blocks ago, processed */
    int32_t *to = gp5_link_out();              /* words for the control processor */
    for (uint32_t i = 0; i < GP5_BLOCK; i++) {
        to[i] = in[i];
        out_left[i] = out_right[i] = back[i];
    }
}

static int fw_command(uint32_t cmd, const uint8_t *p, uint32_t n) { (void)cmd; (void)p; (void)n; return 0; }

nds32/firmware.c:

#include "gp5_firmware.h"
#include "gp5_math.c"                          /* sinf, tanhf ... for this processor (once per firmware) */

static void on_block(const int32_t *in, int32_t *out)   /* in an interrupt, once per block: keep it short */
{
    for (unsigned i = 0; i < GP5_BLOCK; i++) {
        float x = (float)in[i] / 2147483648.0f;
        out[i] = (int32_t)(tanhf(4.0f * x) * 0.5f * 2147483647.0f);
    }
}

void fw_init(void) { gp5_link_start(on_block); }

Try it: python3 tools/simulate.py <folder>. The simulator runs the link with the pedal’s timing.

How it works

  • After each block, the DSP sends link_words words and receives as many. The platform frames them with a sync word and finds them again on the other side; you only see your words.
  • On the control chip, on_block(in, out) runs in an interrupt once per block. in holds the DSP’s words. What you write to out goes back to the DSP.
  • On the DSP, gp5_link_out() takes the words for the control chip during fw_process(), and gp5_link_in() has what came back.
  • Words from the control chip reach fw_process() 3 blocks after the block they were made from.

Rules and limits

  • link_words: a multiple of 8, up to 264. The build rejects larger values. Measured at 48 kHz, 264 words worked; 296 caused dropouts. An exchange takes about 38 % of a block per 128 words. Pack data if you need more values. NAM Loader packs 24-bit samples in block floating point (pack24.h in its repository).
  • link_early: use this if fw_process() takes more than about half a block. Set "audio": { "link_words": N, "link_early": true }, with your word count in place of N. The exchange starts at the start of each block using the previous block’s output. Define static void fw_link_early(const int32_t *in, int32_t *out) on the DSP. The platform calls it before the exchange, so it can put new input into out. NAM Loader uses this path.
  • on_block must finish within a block (1.45 ms; 1.33 ms at 48 kHz). It interrupts the main loop, so the longer it takes, the less time is left for the screen and USB. gp5_link.py status shows its share: keep the worst under about 85 %.
  • Don’t call the platform from on_block. No drawing, no storage, no gp5_param_set. Hand data to the main loop through variables; gp5_log is allowed but costly.
  • A lost exchange repeats or skips a block. Rare, but a long flash write (saving, a computer writing files) can cause it. If your data has state (a model’s history, a sequence), put a counter in a word and check it on the other side, as NAM Loader and Dreamcatcher do.
