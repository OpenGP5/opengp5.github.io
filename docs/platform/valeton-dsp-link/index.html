Valeton's DSP firmware: link commands

The commands Valeton’s DSP firmware answers on the link from the control processor.

What Valeton’s DSP firmware (V1.0.6, the dsp section) understands on the link from the control processor. It was worked out from both firmwares and checked on a pedal. It is here for the DSP updater fault work: on a pedal whose updates stall, Valeton’s DSP firmware stays installed, and an OpenGP5 app can talk to it.

Addresses are DSP addresses in Valeton’s V1.0.6 (its dsp section is loaded at DSP flash 0x4000) or, marked “control”, addresses in Valeton’s control-processor app (runtime address = file offset + 0x10000). Other versions differ. Everything here comes from reading the code and from tests on one pedal; treat it as notes, not a spec.

Sending a command from a computer

The link itself (UART, 460800 baud, framing, CRC) is in Protocols, section 5. OpenGP5’s control firmware passes any payload through to the DSP and returns the answer: 7E 03 stages the payload, 7E 04 sends it (Protocols). From Python:

import gp5_link as gl                    # tools/gp5_link.py
link = gl.open_link()
print(gl.raw(link, bytes.fromhex("00600800 00000000")))   # 0x6000: version query
link.close()

raw() returns (status, reply): status 1 with the reply payload, 0x14 for ACK, 0x13 for NAK, or None.

Not tested yet: today’s OpenGP5 platform running with Valeton’s DSP firmware. An early control firmware of this project did exactly this (November 2026) and drove Valeton’s DSP to full sound with the commands below. The platform’s start-up only needs the version answer, which Valeton’s DSP gives.

Payloads and dispatch

Payload = [cmd u16][len u16 = payload length][fields], little-endian. The command’s high nibble is the group, the low 12 bits the index. Valeton’s dispatcher (0x5C68, jump table at 0x5CD2) has one handler table per group:

Answers: a status-only frame 01 04 00 14 (ACK) for “set” commands, a data frame for queries, nothing for a few. A bad CRC or length gets 01 04 00 13 (NAK).

“state” and “action” are two bytes of the DSP’s control block at 0x20002098 + 0x2E0 / +0x2E1.

Module info (76 bytes): [u16 id][u16][u32][16-byte name][16-byte name][8 × f32 parameters].

0x0000 whole preset (0x170 bytes)

offsetfield
+0x04f32 preset volume
+0x08u16 BPM
+0x0Au16 module enable mask (bit n = module n)
+0x0Cu8 order[10]
+0x18u8 model index[10]: position in that module’s list
+0x24u8 flag[10]: byte 9 of the model’s catalog record
+0x3010 × 8 × f32 parameters

The ten modules: 0 noise gate, 1 boost/comp, 2 drive, 3 amp, 4 cabinet, 5 EQ, 6 modulation, 7 delay, 8 reverb, 9 SnapTone. A wrong flag crashes the DSP when it applies the preset (it calls a missing callback).

0x1000 global settings (0x10 bytes)

+0x04 f32 (sub 4), +0x08 f32 output level (sub 0), +0x0C s8 (sub 1), +0x0D u8 (sub 2), +0x0E u8 (sub 3), +0x0F s8 (sub 5). Only the output level’s meaning is known.

Start-up and sound

Valeton’s control app, after the version query, lists the modules (0x2002 for ids 0–39, 0x7002 for 0–79, then 0x7005) and sends: 0x1000, 0x1001 sub 0 = 0 (mute), 0x6003 0, 0x0000, 0x6003 0. The DSP is silent until 0x6003 3 (run) and 0x1001 sub 0 = 1.0 (output level) follow.

When the DSP crashes

A crash (wrong preset flag, 0x5002 sent first) stops all answers; the pedal goes silent. Unplug the pedal and plug it in again: the DSP starts Valeton’s firmware afresh. Nothing in flash changes, as long as the commands sent didn’t write it.
